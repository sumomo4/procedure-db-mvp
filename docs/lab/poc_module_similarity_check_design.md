# 類似モジュールチェック機能 PoC設計メモ

## 1. 目的

Excelからモジュールを登録する前に、既存モジュールと内容が重複または類似していないか確認できるようにする。

利用者は類似候補と差分を確認し、次のどちらかを選択する。

- 取込内容をそのまま登録する
- 登録を中止してExcelを見直す

本機能は重複登録を機械的に禁止するものではない。最終判断は利用者が行う。

## 2. 対象環境

最初はLab環境へPoCとして実装する。

Labで以下を確認した後、Standardへの反映を判断する。

- 業務上妥当な類似候補が表示されること
- 誤検知と見逃しが許容範囲であること
- 登録操作を妨げない応答時間であること
- 70%というしきい値が妥当であること

## 3. PoCの対象範囲

### 3.1 対象

- Excel取込によるモジュール新規登録
- Excel取込による既存モジュールの新しい版の作成
- 保存前の類似候補表示
- 未保存データと既存モジュールの差分プレビュー
- 類似候補確認後の登録続行または中止

### 3.2 比較対象となる既存データ

PoCでは、各モジュールの最新の承認済み版を比較対象とする。

DB上の状態値では、原則として `published` を対象とする。

既存モジュールの新しい版を登録する場合、同じ `module_key` の過去版は類似候補一覧から除外する。同じモジュール内の版差分は、既存のモジュールdiff機能で確認する。

### 3.3 PoCでは対象外とするもの

- 画像バイナリの類似判定
- AIや外部APIを使った意味的類似判定
- 類似モジュールの自動統合
- 類似候補がある場合の登録禁止
- 原本および案件CSの類似判定
- Standard環境への即時反映

## 4. 用語

| 用語 | 意味 |
| --- | --- |
| 取込モジュール | Excelから解析し、まだDBへ保存していないモジュール |
| 類似候補 | 取込モジュールとの総合類似度がしきい値以上の既存モジュール |
| 詳細比較 | 類似候補と取込モジュールを行単位で比較すること |
| 完全一致 | 比較用に正規化した内容のハッシュが一致する状態 |
| しきい値 | 類似候補として表示する最低類似度。初期値は70% |

## 5. 利用者の操作フロー

```text
Excelファイルを選択
    ↓
Excel取込・正規化
    ↓
類似モジュールチェック
    ↓
┌──────────────────┐
│ 70%以上の候補なし │
└──────────────────┘
    ↓
通常どおり保存

または

┌──────────────────┐
│ 70%以上の候補あり │
└──────────────────┘
    ↓
候補一覧を表示
    ↓
必要に応じて差分を確認
    ↓
「登録を続ける」または「登録を中止」
```

類似チェックが失敗した場合は、チェック未実施のまま通常登録へ進ませない。エラー内容と再実行ボタンを表示する。

## 6. 画面設計

### 6.1 表示位置

モジュール登録画面のExcel取込プレビューと保存操作の間に「類似モジュールチェック」領域を追加する。

### 6.2 候補一覧

最大10件を類似度の降順で表示する。

| 表示項目 | 内容 |
| --- | --- |
| 類似度 | 0～100% |
| モジュールID | `MOD-001`など |
| モジュール名 | 既存モジュール名 |
| 版 | `ver.X.Y` |
| 承認状態 | 承認済み |
| 主な一致項目 | 作業内容、確認事項、コマンドなど |
| 操作 | 差分を見る |

### 6.3 強調表示

| 類似度 | 表示 |
| --- | --- |
| 100% | 「完全一致」の赤い警告 |
| 85%以上100%未満 | 高類似として強く警告 |
| 70%以上85%未満 | 注意候補として表示 |

### 6.4 操作

- `差分を見る`: 未保存データと候補の差分プレビューを開く
- `登録を続ける`: 確認ダイアログ後に保存する
- `登録を中止`: 選択ファイル、プレビュー、類似候補を破棄して登録画面へ戻る

類似候補が1件以上ある場合は、通常の保存ボタンをそのまま押せないようにする。利用者が明示的に「登録を続ける」を選択した場合だけ保存できるようにする。

## 7. 類似度の定義

### 7.1 基本方針

類似度は文章の意味をAIで判定するものではない。

以下の文字列、行構成、コマンド構成の近さを組み合わせて0～100%で算出する。

### 7.2 初期重み

PoCの初期値は以下とする。

| 比較項目 | 重み |
| --- | ---: |
| 作業内容 | 30% |
| 確認事項 / 項目 | 20% |
| 装置別コマンド | 25% |
| 技術資料名・モジュール名 | 10% |
| 行構成・行数 | 10% |
| 対象装置ヘッダー | 5% |
| 合計 | 100% |

式のイメージ:

```text
総合類似度 =
    作業内容類似度 × 0.30
  + 確認事項類似度 × 0.20
  + コマンド類似度 × 0.25
  + 名称類似度 × 0.10
  + 行構成類似度 × 0.10
  + 装置ヘッダー類似度 × 0.05
```

重みと表示しきい値はコードへ直接固定せず、設定値として変更可能にする。

両方のモジュールで空欄になっている比較項目は、総合類似度の重み計算から除外する。片方だけに値がある場合は、その項目の類似度を0%として扱う。これにより、空欄が多いモジュール同士の類似度が不自然に高くなることを防ぐ。

初期しきい値:

```text
MODULE_SIMILARITY_THRESHOLD=0.70
MODULE_SIMILARITY_CANDIDATE_LIMIT=50
MODULE_SIMILARITY_RESULT_LIMIT=10
```

### 7.3 装置別コマンド

装置ごとの差異を保持して比較する。

```text
slot 1: 時刻 / window / P / コマンド
slot 2: 時刻 / window / P / コマンド
...
```

1装置目のコマンドだけを代表値として使用しない。装置番号と行順を含めた比較用文字列を作成する。

### 7.4 画像

PoCでは画像そのものは比較しない。

次のメタデータだけを補助情報として保持する。

- 画像数
- 画像が配置された行
- `anchor_cell`
- 幅と高さ

画像数や配置行が異なる場合は画面へ補足表示するが、初期の総合類似度には含めない。

## 8. 正規化

比較前に入力値を正規化する。

### 8.1 共通正規化

- UnicodeをNFKC形式へ統一
- 改行コードをLFへ統一
- 前後空白を除去
- 連続する空白、タブ、改行を整理
- 空行の表現を統一
- `None`と空文字を同一扱いにする
- 行区切りとフィールド区切りを明示的に付ける

### 8.2 文章項目

英字の大文字・小文字は同一扱いにする。

対象:

- モジュール名
- 技術資料名
- 作業内容
- 確認事項
- 対象装置名

### 8.3 コマンド項目

コマンドでは大文字・小文字が意味を持つ可能性があるため、文字ケースを保持する。

全角・半角と不要な前後空白だけを正規化する。

### 8.4 プレースホルダ

`{{KEY}}`形式のプレースホルダは削除しない。

同じ役割のプレースホルダが一致していることも類似判定の一部とする。

## 9. 検索方式と性能対策

### 9.1 問題

取込モジュールを全既存モジュールと行単位で詳細比較すると、登録件数に比例して処理時間が増える。

毎回すべての行を総当たりする方式は採用しない。

### 9.2 二段階検索

```text
第1段階: PostgreSQLで候補を最大50件へ絞る
    ↓
第2段階: Pythonで候補だけ詳細類似度を計算
    ↓
70%以上の上位10件を返す
```

### 9.3 第1段階

承認済みモジュール版ごとに、比較用の正規化文字列とハッシュを事前保存する。

PostgreSQLの `pg_trgm` を利用し、`combined_text` に対する文字列類似検索で候補を絞る。

日本語の単語解析を前提とせず、文字の並びによる候補抽出を行う。

完全一致はSHA-256ハッシュで先に検出する。

### 9.4 第2段階

候補だけをPython側で比較する。

PoCでは既存diff機能と同じ `difflib.SequenceMatcher` の正規化方針を再利用する。

性能測定で不足する場合は、比較部分を `RapidFuzz` へ置き換える。

### 9.5 暫定性能目標

PoCの暫定目標:

- 承認済みモジュール5,000件
- 1モジュール平均50行
- 類似チェックの応答時間3秒以内を目標
- 候補抽出上限50件
- 画面返却上限10件

これは保証値ではなく、Labで計測するための基準とする。

## 10. DB設計案

### 10.1 比較用シグネチャ

```sql
CREATE TABLE proc.module_similarity_signatures (
    module_version_id bigint PRIMARY KEY
        REFERENCES proc.module_versions (module_version_id)
        ON DELETE CASCADE,
    normalized_name text NOT NULL,
    normalized_work_text text NOT NULL,
    normalized_expected_text text NOT NULL,
    normalized_command_text text NOT NULL,
    normalized_structure_text text NOT NULL,
    normalized_device_header_text text NOT NULL,
    combined_text text NOT NULL,
    exact_sha256 varchar(64) NOT NULL,
    row_count integer NOT NULL,
    image_count integer NOT NULL,
    generated_at timestamptz NOT NULL DEFAULT now()
);
```

候補抽出用インデックス:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_module_similarity_signatures_exact_sha256
    ON proc.module_similarity_signatures (exact_sha256);

CREATE INDEX idx_module_similarity_signatures_combined_text_trgm
    ON proc.module_similarity_signatures
    USING gin (combined_text gin_trgm_ops);
```

### 10.2 シグネチャ生成タイミング

- 新しいモジュール版の登録時に生成
- 承認状態が `published` へ変わった時点で検索対象になる
- 既存の承認済み版はマイグレーションまたは保守コマンドで初回生成
- モジュール版は原則として不変のため、通常は再生成しない

### 10.3 チェック履歴

PoCでは詳細なチェック履歴テーブルは作らない。

登録を続行した場合は、アプリケーションログへ以下を記録する。

- 取込内容のハッシュ
- しきい値
- 候補数
- 最高類似度
- 登録を続行した利用者
- 登録された `module_version_id`

運用上必要と判断した場合、MVP後に履歴テーブルへ移行する。

## 11. API設計案

### 11.1 類似候補チェック

```http
POST /api/v1/modules/similarity-check
Content-Type: application/json
```

リクエストは、`POST /api/v1/modules/import`または`import-sheet`で正規化した `ModuleCreateRequest` を使用する。

レスポンス例:

```json
{
  "result": "success",
  "message": "類似モジュールを確認しました。",
  "data": {
    "threshold": 0.7,
    "checked_count": 50,
    "candidate_count": 2,
    "exact_match": false,
    "input_sha256": "example",
    "candidate_set_sha256": "example-candidate-set-hash",
    "confirmation_token": "signed-short-lived-token",
    "candidates": [
      {
        "module_id": 1,
        "module_key": "MOD-001",
        "module_name": "ログイン確認手順",
        "module_version_id": 10,
        "version_no": 3,
        "display_version": "ver.1.0",
        "status": "published",
        "similarity": 0.92,
        "exact_match": false,
        "score_breakdown": {
          "work_text": 0.95,
          "expected_result": 0.90,
          "command": 0.94,
          "name": 0.80,
          "structure": 0.90,
          "device_header": 0.85
        },
        "matched_fields": [
          "作業内容",
          "確認事項",
          "コマンド"
        ]
      }
    ]
  }
}
```

### 11.2 保存前diff

```http
POST /api/v1/modules/{module_id}/diff-preview?version_no={version_no}
Content-Type: application/json
```

リクエストには未保存の `ModuleCreateRequest` を指定する。

レスポンスは既存の `ModuleDiffData` と同じ形式を基本とする。

既存の `GET /api/v1/modules/{module_id}/diff` は保存済みの2版を比較するAPIであるため、未保存データとの比較には使用しない。

### 11.3 モジュール保存

既存APIを維持し、候補がある場合のみ確認トークンを付与する。

```http
POST /api/v1/modules?similarity_confirmation_token={token}
```

動作:

- 保存時にサーバー側で類似チェックを再実行する
- 70%以上の候補があれば保存せず、`409 Conflict`で候補情報を返す
- 候補確認APIが返した署名付き確認トークンを指定すると保存する
- 確認トークンは、取込内容SHA-256と候補集合SHA-256へひも付ける
- トークンの有効期間は初期値15分とし、期限切れ、改ざん、取込内容変更、候補集合変更を無効とする
- 無効な場合は `409 Conflict` と最新候補・新しい確認トークンを返す
- 候補がなければ、従来どおり保存する

画面だけで制御せず、APIを直接呼び出した場合も確認なしで類似候補を無視できないようにする。
確認トークンは類似候補確認用であり、利用者認証や認可の代替にはしない。

## 12. バックエンド構成案

既存のモジュールDB処理から類似判定を分離する。

```text
app/services/module_similarity.py
    normalize_module_for_similarity()
    build_module_similarity_signature()
    shortlist_similar_modules()
    calculate_module_similarity()
    check_similar_modules()

app/db/module_similarity.py
    upsert_module_similarity_signature()
    list_similarity_candidates()
    backfill_similarity_signatures()
```

既存diffから再利用するもの:

- 文字列正規化の考え方
- 行fingerprint
- 行単位の類似度計算
- `ModuleDiffData`

類似検索固有の処理は既存 `modules.py` へ直接増やしすぎない。

## 13. 画像ファイルの扱い

現在のExcel取込は、保存前プレビュー時点で画像を抽出する。

登録を中止した場合に画像ファイルだけが残らないよう、次のいずれかを実装する。

PoCの推奨:

1. 取込画像を一時ディレクトリへ保存
2. モジュール登録成功時に正式な保存先へ移動
3. 登録中止または一定時間経過後に一時ファイルを削除

類似チェックの導入によって保存前の滞在時間が増えるため、一時画像の後始末も確認対象とする。

## 14. エラー処理

| 状況 | 画面動作 |
| --- | --- |
| Excel解析失敗 | 従来どおり取込エラーを表示 |
| 類似チェック失敗 | 保存を止め、再実行を案内 |
| diff-preview失敗 | 候補一覧は維持し、差分だけ再実行可能にする |
| 候補なし | 通常の保存操作へ進む |
| 候補あり | 明示確認まで保存を無効化 |
| 保存直前に候補が増えた | 409で最新候補を再表示 |

## 15. PoC検証項目

### 15.1 機能

- 完全に同じモジュールが100%として表示される
- 70%以上の候補だけが表示される
- 70%未満の候補が表示されない
- 候補が類似度の降順で表示される
- 最大10件に制限される
- 同じ `module_key` の過去版が候補から除外される
- 1装置目と2装置目以降のコマンド差異が類似度へ反映される
- 候補から未保存データとの差分を確認できる
- 「登録を続ける」でモジュールが1件だけ作成される
- 「登録を中止」でDBにモジュールが作成されない
- 登録中止後に一時画像が残り続けない

### 15.2 正規化

- 全角・半角差だけでは大幅に類似度が下がらない
- 改行コード差だけでは大幅に類似度が下がらない
- 余分な空白だけでは大幅に類似度が下がらない
- コマンドの大文字・小文字差は差異として扱われる

### 15.3 性能

- 候補抽出件数が50件以内である
- 5,000モジュール相当のデータで応答時間を計測できる
- 目標3秒を超えた場合に、DB候補抽出とPython詳細比較の所要時間を分けて確認できる

### 15.4 業務評価

PoC利用者に候補結果を以下で分類してもらう。

- 表示されて妥当
- 表示されたが不要
- 表示されるべきだが出なかった

この結果を基に、しきい値と項目ごとの重みを調整する。
