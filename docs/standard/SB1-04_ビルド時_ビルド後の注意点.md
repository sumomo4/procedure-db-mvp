# SB1-04 ビルド時・ビルド後の注意点

## 1. 目的

本資料は、SB1-04 WebUI構築において、`npm install`、`npm run build`、`npm run dev` を実行する際、およびビルド後に確認すべき注意点を整理する。

## 2. ビルド時の注意点

### 2.1 Node.js / npm のPATH反映

Node.jsをインストールした直後は、既に開いているPowerShellにPATHが反映されない場合がある。

確認コマンド:

```powershell
node --version
npm --version
```

見つからない場合の対処:

```powershell
$env:Path = 'C:\Program Files\nodejs;' + $env:Path
```

または、新しいPowerShellを開き直す。

直接指定する場合:

```powershell
& 'C:\Program Files\nodejs\node.exe' --version
& 'C:\Program Files\nodejs\npm.cmd' --version
```

### 2.2 npm install の権限エラー

今回、`npm install` 実行時に npm キャッシュ作成で権限エラーが発生した。

エラー例:

```text
npm error code EPERM
npm error syscall mkdir
npm error path C:\Users\clove\AppData\Local\npm-cache
```

注意点:

- npmは作業フォルダ外のユーザー領域にもキャッシュを書き込む
- 実行環境の制限や権限不足により失敗する場合がある
- OneDrive配下の作業フォルダでは、同期やファイルロックの影響を受ける場合がある

対処:

- PowerShellを開き直して再実行する
- 権限のあるPowerShellで再実行する
- 必要に応じて、npmキャッシュや `node_modules` がロックされていないか確認する

### 2.3 esbuild の子プロセス起動エラー

Viteは内部で esbuild を利用する。今回、通常権限で `npm run build` または `npm run dev` を実行した際、esbuild の子プロセス起動でエラーが発生した。

エラー例:

```text
Error: spawn EPERM
```

注意点:

- `tsc` の型チェックが通っても、Viteビルドで失敗する場合がある
- Vite設定読み込み時にも esbuild が動作する
- セキュリティソフト、権限、OneDrive同期、実行環境の制限が影響する場合がある

対処:

- 権限のあるPowerShellで `npm run build` を再実行する
- `C:\Program Files\nodejs` をPATHに追加した状態で実行する
- OneDrive同期中であれば、同期完了後に再実行する

### 2.4 package-lock.json の扱い

`npm install` を実行すると `package-lock.json` が生成される。

注意点:

- チーム開発では、依存関係の再現性を高めるため `package-lock.json` をGit管理対象にすることが望ましい
- CIでは `package-lock.json` がある場合、通常は `npm ci` を使う方が再現性が高い
- 今回の初期CI設定では、ロックファイル未作成の状態も考慮し `npm install` としている

今後の推奨:

```yaml
- name: Install dependencies
  run: npm ci
```

ただし、この変更は `package-lock.json` をリポジトリに含めた後に行う。

### 2.5 Node.js バージョン差異

今回ローカルに入ったNode.jsは以下。

```text
Node.js: v24.14.1
npm: 11.11.0
```

GitHub Actionsでは以下を指定している。

```yaml
node-version: 22
```

注意点:

- ローカルとCIでNode.jsのメジャーバージョンが異なる
- 通常のVite/Reactビルドでは大きな問題になりにくいが、依存関係によっては差異が出る場合がある

推奨:

- チームで使用するNode.jsのバージョンを決める
- 必要に応じて `.nvmrc` や `.node-version` を追加する
- CIとローカルのNode.jsメジャーバージョンを揃える

## 3. ビルド後の注意点

### 3.1 dist 配下の成果物確認

`npm run build` 成功後、`dist/` 配下に成果物が生成される。

今回の出力例:

```text
dist/index.html
dist/assets/index-7oH06UV7.css
dist/assets/index-9g-sEM49.js
```

確認観点:

- `dist/index.html` が生成されていること
- CSSとJavaScriptのアセットが生成されていること
- ビルドログにエラーが出ていないこと
- gzipサイズが極端に大きくなっていないこと

### 3.2 dist は通常Git管理しない

`dist/` はビルド成果物であり、通常はGit管理対象にしない。

注意点:

- ソースコードから再生成できるため、基本的にはコミットしない
- GitHub Pagesなど静的ホスティングに直接使う場合のみ、運用方針に従って管理する

推奨:

`.gitignore` に以下を含める。

```gitignore
node_modules/
dist/
```

### 3.3 開発サーバの起動確認

ビルド成功後、開発サーバを起動して画面表示も確認する。

```powershell
npm run dev -- --host 127.0.0.1 --port 5173
```

確認URL:

```text
http://127.0.0.1:5173/
```

確認観点:

- HTTP 200で応答すること
- ログイン画面が表示されること
- ログイン後にHOME画面へ遷移できること
- サイドメニューから各画面へ遷移できること
- 表、フォーム、ボタン、ステータス表示が崩れていないこと

### 3.4 HashRouter のURL形式

今回のWebUIは `HashRouter` を使用している。

URL例:

```text
http://127.0.0.1:5173/#/home
http://127.0.0.1:5173/#/modules/search
```

注意点:

- `#/` 以降がフロントエンド側の画面パスになる
- 静的ホスティングやサーバ設定が未整備でも画面遷移しやすい
- 将来的に通常のURL形式にしたい場合は `BrowserRouter` への変更とサーバ側のリライト設定が必要

### 3.5 外部画像の利用

ログイン画面では外部画像URLを背景に使用している。

注意点:

- オフライン環境では背景画像が表示されない
- 社内ネットワーク制限により画像取得がブロックされる場合がある
- 本番利用ではライセンス、可用性、表示速度を確認する必要がある

推奨:

- レビュー用や社内配布用ではローカル画像に置き換える
- 画像を `src/assets/` または `public/` 配下で管理する

### 3.6 API未接続のモック状態

現在の画面はモックデータで表示している。

注意点:

- 検索、登録、保存、承認変更は実APIには接続していない
- ボタン押下時の細かいエラー制御は未実装
- 入力内容はDBに保存されない

レビュー時の説明:

- SB1-04ではWebUIの基本構成と画面遷移確認が主目的
- API接続は次工程で実施予定
- 画面項目、導線、状態表示の妥当性を確認する段階

### 3.7 画面表示の確認範囲

ビルド成功は、表示品質や操作性の完全保証ではない。

追加で確認すべき観点:

- 画面幅を狭めても文字やボタンが重ならないこと
- テーブルが横スクロールできること
- 入力欄のラベルと値が見やすいこと
- ステータス表示が業務用語と一致していること
- 画面遷移図にある主要導線を辿れること

## 6. 権限周りのまとめ

今回のビルド確認では、通常実行で一部の処理が権限エラーになり、権限付きで再実行することで成功した。

### 6.1 権限エラーが発生した処理

| 処理 | 発生した事象 | 主な原因 |
| --- | --- | --- |
| `npm install` | `npm-cache` 作成時に `EPERM` | npmがユーザー領域へキャッシュを書き込むため |
| `npm run build` | `Error: spawn EPERM` | Viteが内部で使う esbuild の子プロセス起動が制限されたため |
| `npm run dev` | `Error: spawn EPERM` | 開発サーバ起動時にも esbuild が動作するため |

### 6.2 npm install で発生した権限エラー

今回、`npm install` 実行時に以下のようなエラーが発生した。

```text
npm error code EPERM
npm error syscall mkdir
npm error path C:\Users\clove\AppData\Local\npm-cache
```

注意点:

- npmは作業フォルダだけでなく、ユーザー領域の npm キャッシュにも書き込む
- `C:\Users\clove\AppData\Local\npm-cache` への書き込みが制限されると失敗する
- 初回実行時はキャッシュディレクトリ作成が必要になるため、特に発生しやすい

対処:

```powershell
npm install
```

通常実行で失敗した場合は、権限のあるPowerShellで再実行する。

### 6.3 npm run build で発生した権限エラー

今回、`npm run build` 実行時に以下のようなエラーが発生した。

```text
Error: spawn EPERM
```

これは、Viteが内部で利用する esbuild の子プロセス起動が拒否されたことを示す。

注意点:

- `tsc -b` の型チェックが通っても、`vite build` 側で失敗する場合がある
- Vite設定ファイルの読み込み時にも esbuild が使われる
- 開発サーバ起動時の `npm run dev` でも同じ種類のエラーが発生する場合がある

対処:

```powershell
npm run build
```

通常実行で `spawn EPERM` が出た場合は、権限のあるPowerShellで再実行する。

### 6.4 PATH反映との関係

Node.jsをインストールした直後は、現在開いているPowerShellにPATHが反映されない場合がある。

その場合、以下のように `node` / `npm` が見つからない。

```text
node : 用語 'node' は、コマンドレット、関数、スクリプト ファイル、または操作可能なプログラムの名前として認識されません。
npm : 用語 'npm' は、コマンドレット、関数、スクリプト ファイル、または操作可能なプログラムの名前として認識されません。
```

対処:

```powershell
$env:Path = 'C:\Program Files\nodejs;' + $env:Path
```

または、PowerShellを開き直す。

### 6.5 OneDrive配下で作業する場合の注意

今回の作業フォルダは以下のOneDrive配下にある。

```text
c:\Users\clove\OneDrive\デスクトップ\test_UI
```

OneDrive配下では、同期処理やファイルロックの影響で、`node_modules` や `dist` の作成・削除・更新時に失敗する場合がある。

注意点:

- `node_modules` は大量のファイルを生成する
- OneDrive同期中にファイルがロックされる可能性がある
- npmのcleanup処理でディレクトリ削除に失敗する場合がある

対処:

- 同期が落ち着いてから再実行する
- PowerShellやエディタを開き直す
- 必要に応じて、OneDrive配下ではない作業フォルダを使う

### 6.6 推奨する実行順

まずは通常のPowerShellで実行する。

```powershell
node --version
npm --version
npm install
npm run build
```

`node` / `npm` が見つからない場合:

```powershell
$env:Path = 'C:\Program Files\nodejs;' + $env:Path
```

`EPERM` または `spawn EPERM` が出た場合:

- 権限のあるPowerShellで再実行する
- OneDrive同期やファイルロックがないか確認する
- セキュリティソフトが `node.exe` や `esbuild.exe` の実行を止めていないか確認する

```text
今回の環境では、npm install と npm run build は権限付き実行で成功した。
```

今回のビルドでは、Node.js導入後のPATH反映、npmキャッシュ権限、esbuildの子プロセス起動が主な注意点となった。

ビルド自体は成功しており、WebUIの基本構成は成立している。ただし、現在はモックUIであり、API接続、入力値保存、詳細なエラー制御は次工程で対応する必要がある。
