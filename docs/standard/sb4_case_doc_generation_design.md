# SB4 案件化画面 / 案件CS生成設計メモ

## 1. 目的

Sprint 4 では、原本に紐づくモジュールをその順番のまま 1 つの案件CS (`.xlsm`) に展開し、既存テンプレートを流用してダウンロードできる状態を目指す。

- 原本 1 件から案件CS は 1 ファイルだけ生成する
- 出力形式は `.xlsm`
- 既存テンプレートを流用する
- 原本詳細に並ぶモジュールをその順番のまま展開する
- Sprint 4 では生成したファイルをその場でダウンロードするところまでを対象とし、サーバ保存 / 履歴管理は対象外とする

## 2. 現時点で確認できていること

### 2.1 既存データ内のプレースホルダ

ローカルAPIから確認できた既存プレースホルダは以下の 2 種類。

- `{{NW_ADDRESS}}`
- `{{USER}}`

ただし、これらは「現行データで確認できたトークン」にすぎず、今後の案件化設計をこの名前基準で固定する必要はない。
特に `{{NW_ADDRESS}}` は暫定的に使われていたものとし、設計の基準にはしない。
また `{{USER}}` のような値も、原則として画面手入力にはせず、案件化用の共通値テーブルまたは補助マスタから解決する方針とする。

## 3. 案件化画面で最初に選ばせる項目

案件化の入口はサイドバーの `案件化` とする。

1. 原本選択
- `source_doc_id`
- 表示は `source_doc_key + source_doc_name`

2. 設置情報
- `装置設置府県`
- `装置設置ビル`

3. ユニット特定情報
- `FSクラスタ名`
- `ブロック`

4. 案件共通値の解決
- `USER` などの共通値は画面手入力ではなく、案件化用の共通値テーブルまたは補助マスタから解決する

5. 解決結果確認
- `ユニット構成` から解決したホスト割当を表示する
- プレースホルダごとの最終解決値を表示する
- 通常フローでは手入力項目を持たず、どの値がどのテーブルから決まったかを確認できるようにする

## 4. Access データ参照の考え方

1. `ユニット構成` を親として 1 行を特定する
2. その 1 行から `GUI_0系`, `SBC_CL1_0系` などのホスト名を取る
3. ホスト名をキーにして各装置別テーブル (`FS`, `GUI`, `HFS`, `HSS`, `MSW`, `RAID`, `SBC`, `SCCE`) を引く
4. 取得した IP / ID / TTS 情報などをプレースホルダ解決に使う

つまり、`ユニット構成` が案件・装置紐付けの中心になる。

## 5. プレースホルダの考え方

プレースホルダは「手入力して埋めるもの」ではなく、「どのテーブル / どのカラム / どの装置区分から解決するか」というバインド定義で管理する。

### 5.1 分類

1. **共通値マスタ型**
- 例: `USER` のような、案件全体で共通で使う値
- 画面手入力ではなく、案件化用テーブルまたは補助マスタから解決する

2. **ユニット構成直結型**
- 例: 装置設置府県、装置設置ビル、クラスタ名、ブロックなど
- `ユニット構成` の 1 行を決めるためのキーとして使う

3. **装置参照型**
- 例: IPアドレス、TTS-Host、TTS-IP、TTS-Port、CL_ID など
- `ユニット構成` からホスト名を引き、各装置テーブルから取る

4. **互換エイリアス型**
- 例: `{{NW_ADDRESS}}` のような暫定トークン
- これを基準に設計するのではなく、後方互換のための別名として扱う

### 5.2 `{{NW_ADDRESS}}` の扱い

`{{NW_ADDRESS}}` はあくまで一時的に使用していたトークンとして扱う。
したがって、設計上は `NW_ADDRESS` を中心にしてルールを組むのではなく、実際に必要な値と出典カラムの対応を定義する。

例:
- 実際に出したい値: `SBC のコマンド用フローティングIPアドレス`
- 出典: `SBC.xlsx` の `コマンド用フローティングIPアドレス`
- 対象装置: `SBC_CL1_0系` など `ユニット構成` で解決されたホスト

この対応が定まっているなら、表示上の名前が `{{NW_ADDRESS}}` である必然性はない。

### 5.3 手入力前提にしない方針

- 通常フローでは、プレースホルダの値を画面手入力させない
- 値は Access 由来データと案件化用補助マスタから自動解決する
- 手入力は例外対応が必要になった場合のみ、将来的に検討する

## 6. API のたたき台

### 6.1 マスタ選択用

- `GET /api/v1/case-docs/master/prefectures`
- `GET /api/v1/case-docs/master/buildings?prefecture=...`
- `GET /api/v1/case-docs/master/unit-config?prefecture=...&building=...`

### 6.2 解決確認用

- `POST /api/v1/case-docs/resolve-context`
- 入力: `source_doc_id`, `prefecture`, `building`, `fs_cluster_name`, `block`
- 出力:
  - 特定された `ユニット構成` 1 行
  - ホスト割当結果
  - 案件共通値の解決結果
  - プレースホルダごとの最終解決値
- 通常フローでは手入力値を受け取らない

### 6.3 案件CS 生成用

- `POST /api/v1/case-docs/generate`
- 入力: `source_doc_id`, `unit_config_id` または単位を特定できるキー情報
- 処理:
  1. 原本と紐づくモジュールを順番どおり取得する
  2. `resolve-context` 相当の解決を行う
  3. `.xlsm` テンプレートへ値を流し込む
  4. 生成ファイルをバイナリで返す

## 7. テンプレート / バインド定義の考え方

- `.xlsm` テンプレートは backend 側に固定配置する
- テンプレート中の値埋め込み対象は、プレースホルダ名ではなく「必要な値と出典」の定義として管理する
- たとえば `bindings` として「対象セル / 必要値 / 出典テーブル / 出典カラム / 装置区分」を持つ方式が良い

## 8. 推奨方針まとめ

1. 案件化の入口はサイドバーの `案件化` とする
2. 原本、府県、ビル、クラスタ / ブロックから `ユニット構成` 1 行を特定する
3. `ユニット構成` からホストを引き、各装置テーブルから必要値を取る
4. `USER` のような共通値も画面手入力にせず、共通値テーブルまたは補助マスタから解決する
5. `{{NW_ADDRESS}}` は設計基準にせず、必要に応じて後方互換の別名としてのみ扱う
6. Sprint 4 では、仮データであっても `.xlsm` テンプレートを流用した出力まで完了させる
