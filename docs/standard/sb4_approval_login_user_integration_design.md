# 承認機能 ログインユーザー連携方針

## 1. 目的

承認状態確認 / 変更画面で行った操作について、誰が承認・差戻し・保管したかを承認履歴に残せるようにする。

MVP時点では本格的な認証基盤は導入しない。ただしログイン画面は存在するため、フロントエンドだけでテストユーザーとロールを持たせ、承認操作の確認ができる状態にする。

## 2. MVP時点の方針

### 2.1 テストユーザー

MVPでは以下の2ユーザーをフロントエンドに定義する。

| ユーザー名 | パスワード | 表示名 | ロール | 主な用途 |
| --- | --- | --- | --- | --- |
| `member` | `password` | メンバーユーザー | `member` | 閲覧、作成、編集 |
| `approver` | `password` | 承認者ユーザー | `approver` | 承認、差戻し、保管 |

ログイン成功後、ユーザー情報はブラウザの `localStorage` に保存する。

```text
key: mvpAuthUser
```

### 2.2 承認操作の制御

承認状態確認 / 変更画面では、ログイン中ユーザーのロールを見て操作可否を切り替える。

- `member`: 承認状態と履歴は閲覧できるが、状態変更ボタンは実行できない
- `approver`: 承認、差戻し、保管などの状態変更を実行できる

状態変更APIへ送る `changed_by` には、ログイン中ユーザーの表示名を使用する。

### 2.3 コメントとの関係

`changed_by` は「誰が実行したか」を表す。

`note` は「なぜ実行したか / 補足」を表す。

差戻し時は `note` を必須とする。承認・保管時は任意とする。

## 3. MVPの制約

今回のロール制御はフロントエンドだけで行う。

そのため、MVPの画面検証には十分だが、セキュリティ機能としては扱わない。

主な制約:

- ユーザー情報はブラウザの `localStorage` に保存される
- API側ではロールを検証しない
- ブラウザ操作や直接API呼び出しを完全には防げない

社内公開用サーバーとして運用する前には、バックエンド側でも認証・認可を行う必要がある。

## 4. 将来のログインユーザー連携方針

本格認証を導入した後は、承認状態変更時の `changed_by` をフロントエンドから自由に送らない。

想定する流れ:

1. ログイン処理でユーザーを認証する
2. バックエンドがセッションまたはトークンから認証済みユーザーを取得する
3. バックエンドがユーザーのロールを確認する
4. 承認操作が許可される場合だけ状態変更を実行する
5. 承認履歴の `changed_by` にログインユーザーIDまたは表示名を保存する

## 5. 推奨する最終形

最終的には、フロントエンドは「状態変更内容」と「コメント」だけを送る。

```text
フロントエンド
  - 状態変更内容とコメントだけ送る

バックエンド
  - 認証済みユーザーを取得する
  - ロールに応じて操作可否を判定する
  - changed_by をサーバ側で決定する
  - 承認履歴へ保存する
```

この形にすると、画面上の表示だけでなくAPI呼び出しに対しても承認権限を守れる。
