# SB4 案件CSテンプレート本体への原本行差し込み設計

## 目的

現在の案件CS生成では、テンプレートのプレースホルダ置換に加えて、生成結果の確認用として `原本展開` シートへ原本モジュール行を出力している。
次の段階では、確認用シートだけでなく、テンプレート本体の作業明細行へ原本モジュール行を差し込む。

## 現在のテンプレート構造

対象テンプレート:

```text
apps/standard/backend/app/templates/case_docs/case_doc_template.xlsm
```

現在確認できている本体シート:

```text
01.ボーレート確認・修正_CS
```

主な構造:

| 行 | 内容 |
| --- | --- |
| 1行目 | タイトル、対象装置などの上部情報 |
| 4行目付近 | 通番、対象装置ホスト名 `{{TARGET_DEVICE_HOSTNAME}}`。対象装置数により下にずれる可能性がある |
| 5行目付近 | 明細ヘッダー。ただし対象装置数により下にずれる可能性がある |
| 明細ヘッダー直後 | 作業明細。固定行ではなく検出して決める |
| 下部領域 | 連絡事項など。固定行ではなく検出して保持する |

## 明細開始位置の考え方

原本行の開始位置は固定しない。
対象装置が増えると、テンプレート上部の対象装置ブロックが縦に伸び、明細ヘッダーおよび原本行の開始位置が下へずれるため。

そのため、実装では次の順で位置を決める。

```text
1. 本体シートを特定する
2. `大` `中` `小` `作業内容` `確認事項 or 項目` `コマンド` を含む行を明細ヘッダーとして検出する
3. 明細ヘッダー行 + 1 を明細開始行とする
4. `連絡事項` などの下部見出し行を検出する
5. 明細開始行から下部見出し行の直前までを差し替え対象にする
```

これにより、対象装置が横方向・縦方向に増えた場合でも、行番号固定による崩れを避ける。

## 明細の列対応

| 列 | 内容 | 原本データの対応候補 |
| --- | --- | --- |
| A | 大 | `major_no` |
| B | 中 | `middle_no` |
| C | 小 | `minor_no` |
| D | 技術資料名 | `tech_doc_text` |
| E:H | 作業内容 | `work_text` |
| I | 確認事項 or 項目 | `expected_result` |
| J | 時刻 | `time_text` |
| K | window | `window_text` |
| L | P | `p_text` |
| M | コマンド | `command_text` |

## 複数対象装置時の列展開

現在の業務では、対象装置が複数ある場合、作業明細の装置別領域は `J:M` の4列ブロックが右方向に増えていく。

そのため、案件CS生成でも次の構造を基本とする。

| 領域 | 内容 | 増減 |
| --- | --- | --- |
| A:C | 大・中・小 | 共通。対象装置数では増やさない |
| D | 技術資料名 | 共通。対象装置数では増やさない |
| E:H | 作業内容 | 共通。対象装置数では増やさない |
| I | 確認事項 or 項目 | 共通。対象装置数では増やさない |
| J:M | 1台目の対象装置向け `時刻 / window / P / コマンド` | 装置別ブロック |
| N:Q | 2台目の対象装置向け `時刻 / window / P / コマンド` | 装置別ブロック |
| R:U | 3台目の対象装置向け `時刻 / window / P / コマンド` | 装置別ブロック |

つまり、`A:I` は作業内容として共通化し、`J:M` 以降だけを対象装置数に応じて横方向へ複製する。

### 4列ブロックの意味

1つの対象装置ブロックは以下の4列で構成する。

| ブロック内列 | 内容 | 原本データの対応候補 |
| --- | --- | --- |
| 1列目 | 時刻 | `time_text` |
| 2列目 | window | `window_text` |
| 3列目 | P | `p_text` |
| 4列目 | コマンド | `command_text` |

1台目は `J:M`、2台目は `N:Q`、3台目は `R:U` のように、4列単位で右へ増やす。

### 上部対象装置情報との関係

テンプレート上部の対象装置名も、明細ブロックと同じ対象装置順で横方向に並べる。

例:

```text
1台目: M列付近に対象装置1のホスト名
2台目: Q列付近に対象装置2のホスト名
3台目: U列付近に対象装置3のホスト名
```

厳密なセル位置はテンプレートのヘッダー構造に依存するため、実装時は `対象装置` 見出しや `コマンド` 見出しを検出し、4列ブロック単位で複製する。

### 値差し込みの考え方

対象装置ごとに異なる値、たとえばホスト名やIPアドレスは、対象装置ブロックごとに解決する。

例:

```text
J:M  -> SBC_CL1_0 / sbc-tyo-cl1-0 の値で置換
N:Q  -> SBC_CL1_1 / sbc-tyo-cl1-1 の値で置換
```

同じ原本行を横方向の各対象装置ブロックへ展開し、ブロックごとに対象ホストに紐づくプレースホルダ値を使う。

### MVPでの段階的対応

現時点の実装は、1つの対象装置ブロック `J:M` を前提にしている。

次の実装では、まず以下を目標にする。

1. 対象装置一覧を決める
2. `J:M` のスタイルと列幅をテンプレートから取得する
3. 対象装置数に応じて `J:M` ブロックを右方向に複製する
4. 明細ヘッダー行にも `時刻 / window / P / コマンド` を複製する
5. 各明細行の `time_text / window_text / p_text / command_text` を各ブロックへ書き込む
6. ブロックごとに対象ホストの値でプレースホルダを置換する

対象装置一覧は、`resolve-context` の入力で受け取る `target_slot_keys` を使う。
既存互換のため単数指定 `target_slot_key` も残すが、両方が指定された場合は `target_slot_keys` を優先する。

```json
{
  "target_slot_keys": ["SBC_CL1_0", "SBC_CL1_1"]
}
```

`resolve-context` のレスポンスでは、既存互換の `target_assignment` に加えて、選択された対象装置一覧 `target_assignments` を返す。

```json
{
  "target_assignment": { "slot_key": "SBC_CL1_0" },
  "target_assignments": [
    { "slot_key": "SBC_CL1_0" },
    { "slot_key": "SBC_CL1_1" }
  ]
}
```

Excel生成では、`target_assignments` の順番に従って `J:M`, `N:Q`, `R:U`... へ横展開する。

## 差し込み方針

### 第1段階

テンプレート本体の明細領域を、原本に紐づく有効モジュールの行で置き換える。

- 対象は `source_doc.items` のうち `enabled = true` のモジュール
- モジュールは `item_order` 昇順
- モジュール内の行は `row_order` 昇順
- 出力先は本体シートの明細ヘッダー直後
- 明細ヘッダーは固定行番号ではなく、列見出し `大` `中` `小` `作業内容` `確認事項 or 項目` `コマンド` などから検出する
- 対象装置が増えて上部ブロックが縦に伸びても、検出したヘッダー行を基準に明細開始位置を決める
- 明細ヘッダー自体は残す
- 上部の対象装置・プレースホルダ置換は既存処理を維持する
- `原本展開` シートは当面残し、監査・確認用として使う

### 下部領域の扱い

現在のテンプレート例では 51 行目に `連絡事項` がある。
ただし、対象装置数やテンプレート差分により行番号は変わる可能性があるため、固定行番号にはしない。

- 明細ヘッダー直後から、下部領域の直前までを差し替え対象にする
- 下部領域は `連絡事項` などの見出し文字から検出する
- `連絡事項` 以降はテンプレート下部領域として保持する
- 明細行が増える場合は、下部領域の直前に行を挿入する
- 明細行が減る場合は、余った明細行を削除する

## スタイル方針

Excel出力の見た目を崩さないため、既存テンプレートの明細行スタイルをコピーして使う。

- 通常行のスタイルは既存の通常作業行を基準にする
- 大項番行は既存の大項番行を基準にする
- 空行・補足行が必要な場合は既存テンプレートの空行スタイルを流用する
- `E:H` の結合状態は維持する
- 罫線、フォント、塗り、配置、行高をコピーする

## 行タイプの扱い

現時点では、原本行の `row_type` を完全には使い分けない。
まずは以下の簡易ルールで出力する。

| 条件 | 扱い |
| --- | --- |
| `major_no` があり `middle_no = 0` `minor_no = 0` | 大項番行 |
| それ以外 | 通常作業行 |
| `work_text` が空で `expected_result` や `command_text` がある | 補足/確認行として通常行に出力 |

将来的には `row_type` ごとに、見出し行、作業行、確認行、補足行などのスタイルを分ける。

## プレースホルダ置換との関係

原本行に `{{SBC_COMMAND_FLOATING_IP}}` などのプレースホルダが含まれる場合は、テンプレート本体へ書き込んだ後、既存のプレースホルダ置換処理で解決する。

処理順は以下とする。

```text
1. テンプレートを読み込む
2. 原本行をテンプレート本体へ差し込む
3. プレースホルダ値を組み立てる
4. テンプレート全体のプレースホルダを置換する
5. 解決値シート、原本展開シートを書く
6. .xlsm として保存する
```

## 実装対象

主な変更対象:

```text
apps/standard/backend/app/core/case_doc_generation.py
```

追加予定の処理:

- 本体シートを特定する関数
- 明細ヘッダー行を列見出しから特定する関数
- 明細開始行、下部領域開始行を特定する関数
- 原本モジュール行をフラット化する関数
- テンプレート行のスタイルをコピーする関数
- 本体シートへ行を書き込む関数

## 注意点

- `.xlsm` のVBAを壊さないため、引き続き `keep_vba=True` を使う
- 画像は後回しにする
- 条件によるセル色変更も後回しにする
- まずは値と基本スタイルの再現を優先する
- 完全なExcel再現は、実ファイル比較をしながら段階的に詰める

## 次の実装ステップ

1. 本体シートの明細ヘッダー行を検出する
2. 明細開始行と下部領域開始行を検出する
3. 原本行をフラット化する
4. 明細ヘッダー直後へ原本行を出力する
5. 既存のプレースホルダ置換が原本行にも効くことを確認する
6. テストで、生成Excel本体シートに原本行が入ることを確認する
