# Standard本番サーバー 更新時の復旧手順書

作成日: 2026-10-07

`4c4fe7b-routerfix-http80-20261007` への更新に問題があった場合、`7ecf683-http80-20261001` のアプリへ戻す手順です。本番DBを過去時点に戻さず、現在の業務データを保持します。

## 1. 復旧の範囲

- 旧WebUI・APIイメージへ切り替えます。
- ユーザー・権限・モジュール・原本・案件CS・実行記録・storageは現状を保持します。
- 新旧で互換性のない類似度の計算キャッシュだけを削除し、旧方式で再計算させます。業務テーブルは削除しません。
- 追加した `algorithm_version` 列は残し、既定値を1に戻します。
- Docker、PostgreSQLコンテナ、DBボリューム、ネットワーク設定、EDRを変更しません。

この復旧は今回の更新に限ったものです。DB自体の破損、DBボリュームの削除、別版への更新後などは対象外です。

注意: 切り戻すとReact Routerも旧版に戻ります。復旧は障害時の暫定措置とし、利用再開の可否は社内の運用・セキュリティ担当者と判断してください。原因解消後、修正版を再適用します。

## 2. 利用を止める

作業中の利用者へ停止を案内してください。更新時のバックアップ、エラー全文、現在の状態を保存します。

```bash
ssh cnw@10.58.134.28
cd "$HOME/mvp-update/standard-update-4c4fe7b-routerfix-http80-20261007"
sudo docker ps -a
```

更新時の `BACKUP_READY=` のパスを使います。忘れた場合は候補を確認してください。

```bash
sudo find "$HOME/procedure-db-backups/standard" -mindepth 1 -maxdepth 1 -type d
```

`pre-rollback-` ではなく、当該更新時に作成した `日時-4c4fe7b-routerfix-http80-20261007` のフォルダを指定します。

## 3. 復旧実行

以下はSSH接続先で実行します。プロンプトに `BACKUP_READY=` より後の絶対パスだけを入力してください。

```bash
read -r -p "Backup path (BACKUP_READY): " BACKUP
sudo bash rollback_standard.sh --backup "$BACKUP"
```

`Type ROLLBACK to continue:` に `ROLLBACK` と入力します。

スクリプトはバックアップのチェックサム、対象サーバー内の導入先・プロジェクト、DBコンテナ・ボリューム、現在のアプリ版を検証します。別環境・別版と判断した場合は停止します。

復旧開始後はWebUI・APIを停止し、現在のDB・storageも `pre-rollback-日時` へ退避してから旧アプリへ戻します。業務データのダイジェスト一致を確認して再起動します。

`ROLLBACK_OK` を確認してください。エラーになった場合は利用停止を継続し、バックアップを削除せず、エラー内容を確認します。

## 4. 復旧確認

```bash
sudo bash verify_update.sh
```

`VERIFY_OK: 7ecf683-http80-20261001` を確認します。ブラウザでログイン・管理者権限・既存データ・Excel出力を確認してください。旧依存関係へ戻る点を踏まえて利用再開の承認を得ます。類似度キャッシュは次回利用時に再計算されます。

復旧後も `docker-compose.standard.update.yml` を使用します。これはバックアップから読み込んだ旧イメージを固定するためです。手動のCompose操作では4ファイルを指定してください。

## 5. DBやファイル自体の破損がある場合

通常のロールバックではDB・storageのバックアップを上書き復元しません。更新後に追加・修正された業務データを消さないためです。

DBやファイルの破損がある場合は、利用を停止して現在の状態を退避し、以下を確認したうえで復元を別途実施します。

1. どの時点まで戻すか、更新後の入力が失われてもよいかについて承認を得る。
2. `database.dump` と `storage.tar.gz` を同じバックアップ時点の組で使う。
3. まず別DB・別フォルダへ復元して内容を確認する。`pg_restore --list` が成功することだけでは完全な復元確認にならない。
4. 確認後、停止中の本番に承認された手順で復元する。

`down -v`、volume削除、DB初期化SQLの全実行は行わないでください。本資料には業務データを上書きする自動復元コマンドは含めていません。
