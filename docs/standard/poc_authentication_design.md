# Standard ログイン認証設計メモ

## 1. 目的

ブラウザ内の固定ユーザー情報による簡易ログインを廃止し、FastAPIとPostgreSQLが本人とロールを確定する認証へ移行する。

## 2. MVPの方式

- メールアドレスとパスワードはPostgreSQLで管理する。
- パスワードはArgon2idのハッシュだけを保存する。
- ログイン成功時に推測困難なセッショントークンを発行する。
- ブラウザにはセッションを`HttpOnly`、`SameSite=Lax` Cookieとして保存する。
- DBにはトークンそのものではなくSHA-256ダイジェストを保存する。
- ロールは`admin > approver > member`の順で権限を包含する。
- 画面の表示制御は操作補助とし、最終的な認証・認可はAPI側で行う。

## 3. API

| Method | Path | 用途 |
| --- | --- | --- |
| POST | `/api/v1/auth/login` | メールアドレスとパスワードでログイン |
| POST | `/api/v1/auth/register` | 本人がmemberユーザーを新規登録 |
| GET | `/api/v1/auth/me` | 現在のログインユーザーを取得 |
| POST | `/api/v1/auth/logout` | 現在のセッションを失効 |
| POST | `/api/v1/auth/change-password` | 本人が仮パスワードから新しいパスワードへ変更 |
| GET | `/api/v1/auth/users` | 管理者がユーザー一覧を取得 |
| POST | `/api/v1/auth/users` | 管理者がユーザーを追加 |
| PATCH | `/api/v1/auth/users/{user_id}/role` | 管理者がロールを変更 |
| PATCH | `/api/v1/auth/users/{user_id}/active` | 管理者がユーザーを有効化・無効化 |
| PATCH | `/api/v1/auth/users/{user_id}/password` | 管理者が仮パスワードを再設定 |
| DELETE | `/api/v1/auth/users/{user_id}` | 管理者が理由を付けてユーザーを論理削除 |
| POST | `/api/v1/auth/users/{user_id}/restore` | 管理者が削除済みユーザーを無効状態で復元 |

`/api/v1/health`と`/api/v1/health/db`以外の業務APIはログイン必須とする。

## 4. ロール制御

| 操作 | member | approver | admin |
| --- | --- | --- | --- |
| 一覧・詳細参照、登録、編集、案件実行 | 可 | 可 | 可 |
| 承認依頼 | 可 | 可 | 可 |
| 承認、差戻し、保管 | 不可 | 可 | 可 |
| プレースホルダ設定 | 不可 | 不可 | 可 |
| ユーザー追加・ロール変更・有効状態変更 | 不可 | 不可 | 可 |

作成者、承認者、取消者、案件実行者などの監査名は、リクエスト本文ではなくログインセッションから確定する。

## 5. セキュリティ

- 連続ログイン失敗は既定5回で一時ロックする。
- セッションには有効期限を設け、ログアウト時にDB側でも失効させる。
- 状態変更APIは許可された`Origin`からのリクエストだけを受け付ける。
- 本番HTTPS環境ではCookieの`Secure`を必須にする。
- 初期ユーザー投入はPoC限定のブートストラップ設定とし、実運用前にパスワードを変更して設定を無効化する。
- 新規ユーザーのメールアドレスは小文字で保存し、大文字・小文字を区別せず重複不可とする。
- ログイン画面からの自己登録ではロールを選択させず、`member`固定で登録する。
- 自己登録では本人がパスワードを設定するため、登録完了後にそのままログイン状態とし、初回パスワード変更は要求しない。
- 自己登録されたユーザーも管理者向けユーザー管理画面に表示し、ロール変更、無効化、仮パスワード再設定の対象とする。
- 管理者は自分自身のロール変更および無効化を実行できない。
- ロールまたは有効状態を変更したユーザーの既存セッションは失効させる。
- 管理画面およびAPIレスポンスにはパスワードとパスワードハッシュを返さない。
- 管理画面から追加したユーザーは`must_change_password=true`とし、初回ログイン後にパスワード変更を強制する。
- パスワード変更待ちのセッションは、本人情報取得、パスワード変更、ログアウト以外のAPIを利用できない。
- 本人がパスワードを変更すると既存セッションをすべて失効し、新しいセッションを発行する。
- 管理者が仮パスワードを再設定した場合も既存セッションを失効し、再び初回変更待ちにする。
- ユーザー削除は物理削除ではなく、削除日時、削除者、削除理由を保持する論理削除とする。
- 削除時は対象ユーザーを無効化して全セッションを失効し、通常一覧とログイン対象から除外する。
- 自分自身および最後の有効な管理者は削除できない。
- 復元したユーザーは無効状態とし、管理者が内容を確認してから再有効化する。
- 物理削除はWebUIから実行せず、保存期間と監査要件が決まった後の保守作業として扱う。

## 6. 将来拡張

社内テナントとの調整後、Microsoft Entra IDのOpenID Connectへ切り替えられる構造を維持する。アプリ内ロールはEntra IDのアプリロールへ対応付ける。

## 7. 受入観点

- 正しい資格情報だけでログインできる。
- 未ログインの業務APIは401になる。
- 権限不足の操作は403になる。
- ロール階層どおりに操作できる。
- 更新者名をリクエストで偽装できない。
- ログアウト後および期限切れセッションは利用できない。
- ブラウザ更新後も有効なセッションならログイン状態が復元される。
- 未ログインユーザーが自己登録すると、`member`としてログインして利用を開始できる。
- 既存メールアドレスの再登録は拒否され、自己登録で`approver`または`admin`を指定できない。
